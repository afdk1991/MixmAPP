## 1. 决策 1：单仓 workspace + 预留 archive

| 项 | 结论 |
|---|---|
| 形态 | 单一 pnpm workspace，根编排，一个锁文件 |
| 进 workspace | `apps/*`、`services/*`、`packages/*` |
| 不进 workspace | `archive/*`（未来归档）、`infra/*`（配置与 SQL，非 JS 包） |
| 编排入口 | 根 `package.json` 的 `build / test / typecheck / verify`，只覆盖 workspace 内包 |
| 归档规则 | `archive/**` 一律 `paths-ignore`，任何工作流都不因它触发 |

目录目标态：

```
MixmAPP/
├─ apps/
│  └─ app/                 # 端侧应用（@mixmapp/app）
├─ services/
│  └─ api/                 # 后端 API（@mixmapp/api）
├─ packages/
│  ├─ contracts/           # 纯 schema 契约（@mixmapp/contracts）
│  └─ ids/                 # ID 生成（@mixmapp/ids）
├─ infra/
│  ├─ sql/                 # 迁移脚本（PostgreSQL）
│  ├─ nginx/               # 反代配置
│  └─ systemd/             # 服务单元
├─ archive/                # 预留，空目录，不构建
├─ tools/                  # 仓库级脚本（密钥扫描、codemod）
├─ docs/                   # ADR 与运行手册
├─ .github/workflows/      # gate / android / deploy
├─ package.json
├─ pnpm-workspace.yaml
└─ tsconfig.base.json
```

> 说明：这是现有工作树的方向，不额外新建 `core/` 层级——旧仓已被排除，双层结构失去第二层，`core/` 包裹只会多一层路径而无收益。

## 2. 决策 2：统一 `@mixmapp/*`

| 包 | 名称 |
|---|---|
| 端侧应用 | `@mixmapp/app` |
| 后端 | `@mixmapp/api` |
| 契约 | `@mixmapp/contracts` |

规则：

1. 所有跨包引用只用包名，不用相对路径穿越 workspace 边界（tsconfig `paths` 仅作类型提示，运行期由 pnpm 解析）。
2. 新增包必须同 scope，禁止出现 `@mxm/*`、`@afdk1991/*`、`@mim/*` 等历史 scope。
3. 发布包（如需上 npm）必须带 `publishConfig.registry` 且不带 `"private": true`；应用包一律 `private: true`。

## 3. 决策 3：一期 Capacitor，二期评估 Flutter/RN

### 一期
- 端侧以 `apps/app` 为业务实现载体，另建 `apps/mobile`（Capacitor 壳）装载 H5 产物：
  `build:h5 → cap sync android → gradlew assembleRelease`。
- `apps/mobile/android/` 入库；`ios/` 是否入库取决于是否出 iOS 包（本机无 macOS，iOS 只能在 CI/macOS runner 构建）。
- 签名走 Secrets：`ANDROID_KEYSTORE_BASE64`、`ANDROID_KEYSTORE_PASSWORD`、`ANDROID_KEY_ALIAS`、`ANDROID_KEY_PASSWORD`。未配置时只出 debug 包，且作业必须显式标注「未签名」，不得假绿。
- 本机不装 Android SDK：构建与签名在 CI 完成。若需本地 `assembleDebug` 验证，再装 `cmdline-tools + platform-tools + build-tools`，Gradle 用项目自带 wrapper，不装全局 gradle。

### 与现有 uni-app 端的关系（待定项，必须收敛）
- 当前工作树里 `apps/app` 的脚本包含 `build:h5 / build:mp-weixin / build:app / build:harmony`，是 uni-app 多端方案；Capacitor 方案要求一个纯 H5 产物。
- 两条路只能留一条作为主路径，否则构建矩阵翻倍：
  - **A. uni-app 为主**：`build:app` 直接出原生包，Capacitor 取消，二期仍可评估 Flutter/RN。
  - **B. Capacitor 为主**：`apps/app` 只保留 H5 目标，小程序端另行处理，原生壳交给 Capacitor。
- 本 ADR 记录用户当时的选择为 **B（Capacitor）**；若实际落地采用 A，需在本文件追加变更记录，不允许两套并行。

### 二期边界
- 端无关契约放在 `@mixmapp/contracts`，不得引入 DOM/Node 依赖，保证 Flutter/RN 可直接复用 schema。
- 原生替换只替换「壳 + 端侧交互层」，服务端契约不变。

## 4. 决策 4：双活 = 单写多读

### 口径
- **唯一写源**：源站 `services/api` + PostgreSQL；所有 POST/PUT/PATCH/DELETE 回源，边缘不写库。
- **边缘职责**：静态分发、GET 缓存、鉴权前置校验。
- **分流**：按 host + path。写路径（`/api/v1/auth/*`、订单、支付）强制回源；读路径（公开目录、媒体）可走边缘缓存。
- **一致性**：边缘缓存带 `version` + TTL（默认 60s），写成功后由源站 purge；`/health`、`/api/v1/modules` 不缓存。
- **回滚**：`EDGE_READONLY=1` 时边缘退化为纯代理，全部回源，不涉及数据迁移。

### 风险
- 多地域同时写需要数据库层面的多主或分片，PostgreSQL 单主仍是瓶颈；一期只承诺单写多读。
- 「作业绿 ≠ 已上线」：双活必须对源站与边缘各做一次 `curl` 取证，并记录响应头，否则不得把状态改成「已发布」。

## 5. 数据面

- 主库：PostgreSQL（`infra/sql/0001_init.sql` 起，后续按序号递增，只增不改）。
- 无库模式：本地可用内存存储跑通接口与测试，但必须打印显著警告（重启即丢数据），且禁止用于生产。
- 迁移执行：显式 `RUN_MIGRATIONS=1` 才跑，避免应用启动即改库。

## 6. 门禁与 CI 计划

| 工作流 | 触发 | 内容 | 判定 |
|---|---|---|---|
| `api-gate.yml` | `services/**`、`packages/**`、根配置 | `pnpm install --frozen-lockfile` → `pnpm -r typecheck` → `pnpm --filter @mixmapp/api test` → `build` | 任一红即失败 |
| `app-gate.yml` | `apps/**` | 端侧 typecheck + H5 构建 + 产物体积阈值 | 同上 |
| `android.yml` | `apps/**`、`apps/mobile/**` | `build:h5` → `cap sync` → `gradlew assembleDebug/Release` → 上传 APK/AAB | 缺签名只出 debug 并标注 |
| `archive` | — | 无工作流；用 `paths-ignore: archive/**` 取证不触发 | — |

验收：
1. 根 `pnpm install --frozen-lockfile`、`typecheck`、`test`、`build` 全绿。
2. `apps/mobile` 能出可安装 debug APK；release 在签名齐备后出 AAB。
3. `EDGE_READONLY=1` 时写入全部命中源站（响应头取证）。
4. 改 `archive/**` 不触发任何构建。

## 10. 变更记录 · 2026-11-12（收敛结论：A 为主，B 仅作打包壳）

**决策来源**：用户在本会话通过选项确认「技术底座 = uni-app 单码多端（Vue3 + TS）」，「所有 APP 端 = Web/H5/PWA + Android/iOS 原生壳 + 鸿蒙」，并选定三套 ID 策略并存、四类第三方全接。

**结论**：

| 项 | 结论 |
|---|---|
| 业务实现唯一载体 | `apps/app`（uni-app），四个目标 h5 / mp-weixin / app / app-harmony 全部本地编译通过 |
| 原生壳定位 | `apps/mobile`（Capacitor）**不再是第二套实现**，只作为「把同一份 H5 产物装进安卓 WebView 并出 APK/AAB」的打包工具 |
| 构建矩阵 | 不再互斥：uni-app 负责出各端资源，Capacitor 只消费 `apps/app/dist/build/h5`，产物同源，不存在两套业务代码 |
| 签名流程 | 只有一套：`ANDROID_KEYSTORE_*` secrets + `apps/mobile/android/app/build.gradle` 的 `hasReleaseSigning` |
| iOS | 仍走 uni-app `build:app` 后由 macOS / HBuilderX 打包；本机无 macOS，不做本地验证 |

**验收状态**：

- `pnpm verify` 全绿（规则 / 类型 / 33 例测试 / API 构建 / H5 构建）。
- `apps/mobile` 已实际产出 `app-debug.apk`（约 4.15 MB）与未签名 `app-release.aab`（约 3.03 MB）。
- Android release 签名仍未验证（缺 keystore），CI 中未配置 secrets 时只出 debug 并显式 warning，不假绿。

**因此 ADR 原文 §3「两条路只能留一条」的顾虑已解除**：uni-app 是唯一实现来源，Capacitor 是可替换的打包外壳；若将来换 Flutter/RN，只需替换外壳，服务端契约不变。
